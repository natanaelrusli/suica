# Suica

A personal background agent for macOS that polls GitLab on `repo.madhani.one` and shows a notification when someone requests your review (flow A) and when someone reviews or comments on your own merge requests (flow D). Vocabulary: [CONTEXT.md](CONTEXT.md). Design: [spec](docs/superpowers/specs/2026-10-14-mr-review-assistant-design.md). Plan 1 (alerts), Plan 2 (Teams chats) and Agent Review (see below) are implemented.

It only reads from GitLab, apart from posting an Agent Review as you and approving an MR you approve with one click (or automatically, with `review.approve`) and resolving your own threads on it. With Teams enabled it also chats colleagues as you, from fixed templates, introducing itself by name.

It comes as two apps, each installed on its own from this repository:

- **The `suica` CLI** (`src/`): the commands and the background agent that polls GitLab. `scripts/install-cli.sh` installs it under `~/.local`, so it keeps working when the checkout moves or changes; `suica agent install` starts the background agent.
- **Suica.app** (`macos/`): the menu bar app and its window. It runs the installed `suica` command for everything, so install the CLI first.

## Requirements

- Node 24 (see `.nvmrc`), for the CLI
- Swift (Xcode or the Command Line Tools), to build the app; macOS 15 or later to run it (the Office page uses RealityKit's `RealityView`)
- [`glab`](https://gitlab.com/gitlab-org/cli) logged in to `repo.madhani.one` (`glab auth status`)
- Optional: `terminal-notifier` (`brew install terminal-notifier`) so that clicking a notification opens the MR, or Suica's Messages for a Re-review Nudge. Without it the agent falls back to `osascript` and the notification is not clickable.

## Setup

Clone the repository and run everything below from its root. `make` lists every target, and each one is a thin wrapper over the script or command named beside it, so you can run those directly instead.

Check the requirements first: `node --version` (24 or newer) and `glab auth status`. The CLI alone is all you need to get notifications; add the app when you want the window, the menu bar badge and one-click actions.

### Option 1: CLI only

The `suica` command and the background agent. Nothing is built, and no Swift is needed.

```bash
make install        # install-cli + config + agent-install, in that order
make status         # check that the agent is running and polled
```

or the same by hand:

```bash
scripts/install-cli.sh               # installs ~/.local/lib/suica and the command ~/.local/bin/suica
mkdir -p ~/.config/suica
printf 'gitlab:\n  hostname: repo.madhani.one\n' > ~/.config/suica/config.yaml
suica agent install                  # starts the background agent (see Run in the background)
```

`make config` writes the config file only when none exists; set `GITLAB_HOSTNAME=<host>` to use another GitLab host. Put `~/.local/bin` on your `PATH` (the install script tells you when it is not). Without that, `make` still works: it runs the command by its full path.

### Option 2: CLI and the menu bar app

Install the CLI first, as above, because Suica.app runs the installed `suica` command for everything. Then build and install the app; this needs Swift (Xcode or the Command Line Tools).

```bash
make install        # Option 1
make install-app    # builds, installs ~/Applications/Suica.app and starts it
```

or by hand: `scripts/install-macos-app.sh` after the three CLI steps. The app bakes in the absolute path of the `suica` command it finds (set `SUICA_CLI` for another one), so run `make install-app` again if the CLI moves. Add Suica under System Settings → General → Login Items to start it at login (see Menu bar app).

### Update and remove

```bash
make update         # CLI from this checkout; restarts the agent if it is installed
make update-app     # CLI and app
make uninstall      # app, agent and CLI; config, state database and logs stay
```

`make uninstall-cli` and `make uninstall-app` remove one of them. After switching Node versions, run `make update` (and `make install-app` if the CLI path changed); coming from the old name, run `make migrate` first (see Moving from MR Review Assistant).

### Everyday commands

```bash
make status | once | pause | resume    # the suica commands of the same name
make restart                           # apply config edits
make logs | errors                     # follow the agent's output or error log
```

### What the install script does

`scripts/install-cli.sh` copies `src/` with `package.json` and `package-lock.json`, installs the production dependencies with `npm ci --omit=dev --ignore-scripts`, and writes `~/.local/bin/suica`, a two-line wrapper with the absolute path of the `node` it found (Node 24 or newer). Set `SUICA_PREFIX` to install somewhere other than `~/.local`, and put `<prefix>/bin` on your `PATH` (the script tells you when it is not). Re-run it to update from the checkout, and after switching Node versions. When a LaunchAgent is already installed, the script runs `suica agent install` again so the agent uses the new copy right away. `scripts/uninstall-cli.sh` stops and removes the agent and the installed CLI; the config, state database and logs stay.

## Commands

```bash
suica once      # one poll now
suica status    # paused / baseline / tracked counts
suica pause     # stop polling (kill switch)
suica resume
```

The app window (below) runs these commands. They print one JSON document on stdout, can be used from a script, and (except `stats` and `usage`) work even when the config file is broken:

```bash
suica status --json         # agent service, last poll, paused, intervals, paths, installed model CLIs; a broken config shows up as configError
suica stats                 # history statistics: last 14 days per day, turnaround over 30 days, people and approvals over 90 days
suica usage                 # language model tokens: last 24 h, 7 and 30 days, by purpose, last 14 days per day
suica office --json         # the Coding Agents running on this Mac: Claude Code, Codex, Gemini CLI and any office.custom agent, one entry per Session
suica office chat <agent> <sessionId> --json  # the last 40 messages of one Session's conversation, for the Office's chat panel
suica config show --json    # every config key with the value in the file, the effective value, and the problems found
suica config set --json     # applies edits read from stdin (see below)
suica agent restart --json  # launchctl kickstart -k of the background agent
suica reviews --json        # you, and the open MRs where you are a Reviewer (asks GitLab through glab)
suica mr <key> --json       # one MR by key (group/project!12): description, reviewers, pipeline, squash, discussions, diff
suica mr approve <key> <sha> --json  # approve the MR as you, only if its head commit is still <sha>, then resolve your open threads
suica review queue <key> --json    # queue an Agent Review of that MR; the background agent starts it within a few seconds
suica review post <id> [--inline|--comment] --json  # post a ready review to GitLab as you (default: review.postAs)
suica review discard <id> --json   # drop a ready, failed or skipped review
suica review cancel <id> --json    # stop a queued or running review (the background agent stops a running one within seconds)
suica mr comment <key> --json      # post the Markdown on stdin as a comment on the MR, as you
suica mr close <key> --json        # close an MR you wrote, without merging
suica mr merge <key> <sha> [--squash] [--remove-source-branch] [--when-pipeline-succeeds] --json  # merge at <sha>, commit message on stdin
suica fix list --json              # open Agent Fixes and those of the last 7 days
suica fix queue <key> --json       # queue a fix of every open thread on your MR whose newest note is someone else's
suica fix queue <key> --pipeline --json  # queue a fix of your MR's failed head pipeline
suica fix confirm <id> --json      # commit, push and reply; your edits as JSON on stdin
suica fix retry <id> --json        # drop the fix and queue a new one for the same threads; your note on stdin
suica fix discard <id> --json      # drop a ready or unpushed fix
suica fix cancel <id> --json       # stop a queued or running fix
suica fix replies <id> --json      # post the replies a pushed fix could not post
```

`mr comment` prints `posted`, `empty`, `bad-key` or `failed`. `mr close` prints `closed`, `not-yours` (the signed-in GitLab user did not write the MR), `bad-key` or `failed`. `mr merge` prints `merged`, `scheduled` (GitLab merges once the running pipeline succeeds, with `--when-pipeline-succeeds`), `not-mergeable` (GitLab answered 405 or 406), `sha-mismatch` (someone pushed past `<sha>`, so nothing merged), `bad-key` or `failed`; a blank message leaves GitLab's default. `fix confirm` reads `{"commitMessage": "…", "threads": [{"id": "gid://gitlab/Discussion/…", "reply": "…", "post": true}]}` and prints `pushed`, `partial` (pushed, but some replies failed: `fix replies` posts the rest), `branch-moved`, `push-failed`, `bad-request` (an id the fix does not have) or `nothing`.

`reviews` and `mr` read GitLab directly, not the state database, so they need a working config and `glab` login. `mr` fetches at most 100 discussions and 100 changed files, and leaves out a file's diff when GitLab marks it too large, when it is over 200,000 characters, or once 1.5 million characters of diff have been included (`diff` is then `null`). `mr approve` prints `{"status": …}`: `approved`, `head-changed` (the source branch moved past `<sha>`, so nothing was approved), `bad-request` (malformed key or commit) or `failed`. After `approved` it resolves every open thread you started on the MR (your own comments and an Agent Review's inline threads); threads others started stay open, even where you replied. A thread GitLab refuses to resolve is logged and left; the status stays `approved`.

`config set --json` reads at most 1 MiB from stdin:

```json
{ "baseSha256": "<sha256 from config show, or null if the file does not exist>",
  "edits": [{ "path": ["polling", "activeSeconds"], "value": 90 }] }
```

A `value` of `null` removes the key, so the agent's default applies. It prints `{"status": …, "issues": [{"path": …, "message": …}], "sha256": …}` and exits 0 only for `saved`. The other statuses write nothing: `invalid` (the edited config would not load, or the templates folder does not load (notification templates always, Teams templates when Teams is on); `issues` names the keys), `conflict` (the file changed since `baseSha256` was read) and `bad-request` (not a valid request: not JSON, not the shape above, larger than 1 MiB, or it names a key that does not exist). A save is atomic and the file is written with mode `0600`. `agent restart --json` prints `{"status": …}` with `restarted`, `not-installed` or `failed` and exits 0 only for `restarted`.

## Agent Review

The agent can review a merge request with a coding agent CLI following a Claude Code skill (`review.skill`, by default `madhani:madhani-code-review`), and the review waits in the app until you post it.

- **Start**: with `review.auto` (on by default), every poll queues each MR waiting for you (not a draft, your state still not reviewed) that the agent has never reviewed, oldest first, and an MR that asks for your review again; at most `review.maxPerDay` a day. **Re-review**: once the Author's latest push (a new head commit on an MR waiting for you or already reviewed by you, not a draft, and not one you approved: once you approve an MR, or the agent approves it as you with `review.approve`, the agent stops re-reviewing it, unless the approval is taken back, for example by a project that removes approvals on a push) has stood for `review.rereviewAfterMinutes` (10 by default), so several pushes in a row make one review, and the newest posted-or-discarded review of the MR was posted (a discarded one is not followed up) at another commit, an Agent Re-review is queued, after the first reviews, within the same `review.maxPerDay` cap. Each head is queued once. The head an MR has when Suica first sees it counts as queued, so an upgrade never re-reviews a head that had not moved, and so does a head whose newest review is already ready, being posted or posted (one you started with **Review again** during the wait, say). A push made while a review of the MR runs is re-reviewed once that run is done; a review still queued reviews the head it finds when it starts. A failed, skipped, discarded or cancelled review is not retried on its own; **Review again** still queues one by hand. An MR whose last posted-or-discarded review was posted, and whose head Suica tracks, is not reviewed again the moment it asks for your review again after a push: the re-review's wait decides. An MR re-added after a push that Suica did not track is queued at once, unless its newest review already covers its head, and runs as an Agent Re-review (labelled "Agent re-review", with the `notice.refindings` Review Notice). **Review with agent** on an MR in the window (or `suica review queue <key> --json`) queues one by hand. The background agent starts the oldest queued reviews within about two seconds, up to `review.concurrency` (2 by default, at most 4) at the same time, each with its own CLI process and checkout, beside the poll loop (an MR never has two at once); nothing runs while polling is paused. A review running when the background agent stops or restarts goes back to the queue and runs again after the restart, without a notification. **Cancel review** on the **Agent review** tab (or `suica review cancel <id> --json`) stops a queued or running review: a queued one never starts, and the background agent notices a running one within two seconds, stops the clone or the CLI, deletes the checkout and sends no notification. A cancelled review does not count toward `review.maxPerDay`, and the head it would have reviewed is not queued again on its own; **Review again** queues a new one.
- **Run**: the agent reads the MR and its diff from GitLab, skips drafts and MRs over `review.maxChangedLines`, clones the source branch shallowly with `glab repo clone` into a temporary folder (deleted afterwards), and skips a commit that already has a ready or posted review. The CLI from `model.cli` then reviews, with `review.model` when set, `mr.diff` (GitLab's diff against the target branch) with the checkout for context. **Claude Code** runs the skill natively (`/madhani:madhani-code-review`), with only the Read, Grep, Glob and Skill tools, everything else refused (`--permission-mode dontAsk`) and no MCP servers (`--strict-mcp-config`), so it cannot run commands, reach the network or message anyone. **Codex** runs in its read-only sandbox without MCP servers and gets the skill's `SKILL.md` and `references/*.md` pasted into the prompt; the other skills it points to are not available to it. **Gemini CLI** is not supported for reviews: the run fails with a message saying so. The prompt marks everything from the MR as untrusted and asks for the skill's normal mode, never `--brutal`, with the scope stated as code reading only. Tokens are recorded under **Token usage**. A notification (in Indonesian, like the others) says when a review is ready, skipped or failed.
- **Post**: with `review.post: approval` (the default), open the MR in **Review requests → Agent review**, read it, then **Post to GitLab…** (asks first, with **Post inline** and **Post as one comment**) or **Discard**. With `review.post: auto` the review is posted the moment it is ready, and the notification says it was posted (or that posting failed, in which case it waits in the app like an approval-mode review). It is posted as you, as one MR comment starting with a line saying an agent wrote it, or inline (`review.postAs: inline`, or **Post inline**): each finding listed under a heading named Findings that starts with a `` `path:line` `` code span on a line of the diff GitLab keeps for the reviewed commit becomes a diff thread on that line, labelled the same way, and the comment keeps the rest of the review with each of those findings cut to a pointer. Positions use the reviewed commit's version, so a later push leaves the threads on the code that was reviewed (GitLab shows them as outdated). A finding whose file or line is not in that diff, or whose thread GitLab refuses, stays in the comment; afterwards the review says how many findings went inline. A range such as `path:4-9` is placed on its first line. Before posting, lines starting with `/` are escaped so GitLab does not run them as quick actions, and @mentions and links outside code are removed. The agent never requests changes. With `review.approve` (on by default; turn it off to approve yourself with one click on **Approve** in the app) it approves the MR as you right after an Agent Review that is **ready to approve** is posted. Such a review does not wait for you: it is posted and approved the moment it is ready, even with `review.post: approval`, and the notification says so; a review that is not ready to approve waits as before. `review.approveWhen` sets how strict ready to approve is: with `minor` (the default) every finding is Minor or Nit, and every open item of its `## Previous review` section names Minor or Nit and nothing more serious; with `nit` the same with Nit only; with `clean` the review has no findings and no open item (a finding or item without a severity counts as serious) (design: [approval strictness spec](docs/superpowers/specs/2026-10-21-approval-strictness-design.md)). The approval is tied to the reviewed commit, so a push since the review makes GitLab refuse it; the review's note then says so (also when GitLab refused for another reason) and nothing is retried. Once approved, it resolves every open thread you started on the MR, as **Approve** does, and the note says how many (or to check GitLab when one could not be resolved). This covers a first Agent Review too; an MR that was already ready when you switch the setting on is approved only after its next posted review. The notification after an automatic post says when the MR was approved too. A post that fails goes back to ready with a note to check GitLab first, since the comment may have arrived; when inline threads were posted but the comment was not, the note says so, because posting again repeats them.
- **Re-review**: an Agent Re-review (the review runs as a re-review whenever the newest posted-or-discarded review before it was posted at another commit, including one started with **Review again**) gets the previous review in `./previous-review.md` (marked untrusted like the MR) and, when GitLab's compare API can give it, `./since-last-review.diff`, the diff from the commit the previous review covered to the new head; it reviews only those changes and uses `./mr.diff` for context. When that commit is no longer an ancestor of the head (a rebase or force-push), GitLab cuts the compare off at its timeout, or GitLab fails, the whole MR is reviewed and the scope says so. The review opens with a `## Previous review` section listing every open item of the previous review, and of its own `## Previous review` section, as fixed, not fixed or partly fixed with one sentence of evidence; the findings below it are problems in the new changes only. That section is never counted as findings. On GitLab the note and inline threads read "Agent re-review" and name the commit the previous review covered; the app marks the review with a **Re-review** badge on the **Agent review** tab. A change to the MR's description alone (the head unchanged) is not re-reviewed on its own: the review requests list marks the MR (below) and **Re-review** queues one by hand, which runs as a re-review at the same commit, without `./since-last-review.diff` and with the prompt saying only the description changed. Each review records a hash of the description it read, so a run at a commit and description that already have a ready or posted review is still skipped.
- **What it is doing**: Overview has an **Agent Review** card with the MR being reviewed now (title, CLI, model, for how long, and its newest step, as the menu bar panel shows too) and **Cancel review**, the next ones in the queue (each with **Cancel review**), the reviews ready to post with **Post to GitLab…** (asks first, as on the Agent review tab), and under **Settings** whether automatic reviews are on and pickers that save one key each and apply after **Restart agent**: **Posting** (wait for me, or post automatically, which asks to confirm first), **Post as** (`review.postAs`: one comment or inline threads, used by automatic posting) **Model** (CLI default, or `opus`, `sonnet`, `haiku` when Claude Code reviews; other names go in Configuration) and **Effort** (`review.effort`, a slider from Low to Max); the menu bar popover shows the same "Reviewing …" line while a review runs, with **Cancel review**. `suica status --json` and `suica state` carry it as `agentReview`. Each review records the model that wrote it, as the CLI reported it.
- Reviews are kept for 90 days. A run cut off by a restart is marked failed when the agent starts again. A post still under way after 15 minutes was cut off (`suica review post` stopped by the app's timeout, a crash or a reboot): when the agent starts or the review list is read (`suica reviews --json`, which the app reads every 3 to 15 seconds while a review is active), it goes back to ready with a note to check the MR in GitLab before posting again, since some comments may have arrived.

## Agent Fix

Suica watches your own open MRs and answers the Reviewers' threads with a coding agent CLI. Nothing reaches GitLab until you confirm.

- **Watch**: with `fix.auto` (on by default), every poll looks at each of your open MRs (drafts too) that is not yet approved, approved meaning it has Reviewers and every one of them approved. It reads an MR's threads only when someone else wrote a new note, when it never read the MR, or when the MR's last fix ended since. A **Finding Thread** is an unresolved, resolvable thread whose newest note is someone else's, bots included. A thread a fix handled stays quiet until someone writes on it again. When the threads are new, a fix is queued (at most `fix.maxPerDay` a day). An MR has at most one open fix: new threads join a fix that is still queued, or wait until the open one ends. Once the MR is approved a queued fix is cancelled; a ready one stays for you. When the MR is merged or closed its open fixes are dropped. **Fix findings now** on the MR (or `suica fix queue <key> --json`) queues one by hand, of every open thread whose newest note is someone else's.
- **Run**: one fix at a time. The agent clones the source branch shallowly over SSH into a `fixes/<id>` folder beside the state database, kept until you decide. The CLI gets the MR in `./mr.md` and the threads in `./threads.md`, both marked untrusted. Claude Code may only read and edit files (no shell, so nothing runs and nothing reaches the network); Codex runs in its `workspace-write` sandbox. For each thread it changes the code, or drafts a reply saying why nothing should change, and ends with a JSON block naming each thread. A change over 500,000 characters fails the fix. Tokens show as **Agent fixes** on Token usage.
- **Confirm**: open the MR under **Your MRs** on the Review requests page, then the **Agent fix** tab. It shows each thread with the Reviewer's notes, whether the code changed, an editable reply and **Don't post**, then the commit message and the diff. **Confirm and push…** checks that the branch has not moved since the fix was made, commits with your git identity, pushes as a fast-forward (never with force, never skipping hooks), and posts one reply per thread, with `{{sha}}` replaced by the short commit. The Reviewers resolve their threads. **Retry with a note…** drops the fix and starts a new one on a fresh checkout with your note. **Discard** drops it.
- A failed fix marks its threads handled, so it is not retried on its own; **Retry with a note…** or **Fix findings now** runs it again. A fix running when the background agent stops goes back to the queue. A confirm cut off for 15 minutes becomes "not pushed", or "pushed" when the push went out.
- **Only your MRs**: queueing, running and confirming a fix each check that the signed-in GitLab user wrote the MR (`not-yours` otherwise). The model works in `fixes/<id>/work`; the git folder is `fixes/<id>/git`, outside its reach, every git command names both, and a fix fails if the git settings changed during the run. Lines of a reply that start with `/` are escaped, so no GitLab quick action runs as you. Cancelling a fix, or a push that fails, keeps its threads quiet until someone writes on them.
- **Pipeline Fix**: every poll also reads the head pipeline of each of your open MRs. When one fails (a new pipeline that failed, or the same one going from running to failed) you get a notification (`alert.pipeline-failed`) and, with `fix.auto` and `fix.pipelines` (both on by default), a **Pipeline Fix** is queued: an Agent Fix of the failed pipeline instead of threads, counted in `fix.maxPerDay`. The first poll after upgrading only records the pipelines, so it sends nothing. An MR whose fix is running or waits for you gets no second one (the failure is logged); a Pipeline Fix joins a fix of the MR that is still queued, and one run then answers the threads and fixes the pipeline in one commit. **Fix pipeline** on one of your MRs whose pipeline failed (or `suica fix queue <key> --pipeline --json`) queues one by hand (`no-failed-pipeline` otherwise). The run reads the jobs that failed the pipeline (every failed job when all were allowed to fail), at most five, and the last 300 lines (at most 20,000 characters) of each job's log, without colour codes, section markers and timestamps, into `./pipeline.md`, marked untrusted like the MR. The model works in the same sandbox as for threads, so it cannot run the failing command: it reads the logs and the code, changes what it can, and ends with a sentence on why the jobs failed. A Pipeline Fix that changes no code (a flaky test, a runner problem) ends as skipped with that sentence, and you get `alert.fix-failed` with it; one with a change waits for you like any fix (`alert.pipeline-fix-ready`), and the **Agent fix** tab shows the pipeline, each failed job with a link to its log, and the sentence. Job logs are never stored: the fix keeps the pipeline's number and link, each failed job's name, stage and link, and the sentence. **Retry with a note…** reads the pipeline's jobs again. Once the MR is approved, a queued Pipeline Fix stays queued (only a fix of threads alone is cancelled). Your MR rows show **Pipeline failed**, **Pipeline running** or **Pipeline passed** (design: [pipeline fix spec](docs/superpowers/specs/2026-10-21-pipeline-fix-design.md)).
- **Close**: **Close MR…** on your MRs (asks first) closes the MR without merging; its fixes are dropped at the next poll.
- **Comment** and **Merge**: on your MRs the Comments tab has a comment box with a Markdown preview, and the header has **Merge…**. It merges only the commit the sheet opened on: after a newer push it says so and stays off. The Merge sheet picks squash (locked when the project decides), delete source branch and the commit message each time, and merges at the commit on screen. While the pipeline runs the button reads **Merge when pipeline succeeds**. When GitLab will not merge (no approval, a failed pipeline, conflicts, a draft, unresolved threads, a rebase needed) the button stays off and says why.

## Teams

Teams is off until `teams.enabled: true`. Messages are chats from you, written from Indonesian templates you can edit (below), sent as Markdown and never by a language model. Every built-in template opens with the agent introducing itself by the name in `teams.agentName` (`Suica` by default): "Halo Rina, saya Suica, agen review-nya Nata."

- **Reviewer Nudge** to a Reviewer who is added to, or re-requested on, one of your non-draft MRs; one reminder if they are still `UNREVIEWED` 24 hours later; never to someone who already reviewed.
- **Review Notice** to the Author of an MR you reviewed: after you approve it, at the first poll that sees the approval, in its own send mode (`teams.modes.approved`, `auto` by default); after you request changes or leave comments only, 10 minutes after you stopped changing your review (`teams.modes.notice`).
- **Review Notice with findings** to the Author once an Agent Review of their MR is posted: "Halo <name>, saya sudah review MR kamu: ada 8 findings (7 Minor, 1 Nit)." with the MR link, or "tidak ada findings". It counts every numbered or bulleted item under the review's Findings heading per severity subheading, or a line that is only a bold severity such as **Minor** (Blocker, Major, Minor, Nit, in that order; items under another subheading, such as "Outside this diff", are left out). It goes out at the first poll that sees the review's comments, without the 10-minute wait (or after it, should the comments never show), and it stands in for the plain "comments" Review Notice for those comments; an approval or request for changes later still gets its own Review Notice. It is sent without asking by default (`teams.modes.findings: auto`), inside working hours like every message. Only MRs where you are a Reviewer get it, and an Agent Review posted before Suica saw the MR (or before this version) is never announced. After an Agent Re-review is posted, the Review Notice is `notice.refindings` instead, which reports only the new findings ("Halo <name>, saya sudah review ulang update MR kamu: ada 2 findings baru (1 Major, 1 Minor).", or "tidak ada findings baru"); the previous review's items are not counted. It uses the same `teams.modes.findings` mode and rules. When the agent approved the MR after that re-review (`review.approve`), the notice is `notice.reapproved` instead (after an approved first review the Author gets the findings notice, then the usual approved notice) ("Saya sudah review ulang update MR kamu: tidak ada findings baru, jadi MR-nya sudah saya approve.") and it counts as the approval's Review Notice, so no plain "approved" notice follows.
- **Re-review Nudge** to a Reviewer of your non-draft MR who had already reviewed it (approved, requested changes, reviewed, or left at least one comment) after you pushed new commits: once the head commit has stood for `teams.rereviewAfterMinutes` (10 by default), so several pushes in a row make one message. It is one per round: the next one for the same Reviewer and MR needs them to review again first (a new comment, or a new review state; a reset to `UNAPPROVED` or `UNREVIEWED` by GitLab's push does not count), and then another push. It waits for your approval by default (`teams.modes.rereview`), and in `approval` mode a macOS notification on your Mac says so (below). Commits that were already there when Suica first saw the MR, or when Teams was switched on, are never announced; a draft keeps its record but gets no nudge until it is marked ready (then a Reviewer whose review predates the current head is nudged after the same wait). A Reviewer never gets both a Reviewer Nudge and a Re-review Nudge for one head: when GitLab resets their state in the poll in which you pushed, they get the Re-review Nudge, and when you press GitLab's re-request without pushing, they get the Reviewer Nudge and a Re-review Nudge still waiting for you is skipped. Re-review Nudges do not count towards `teams.maxMessagesPerReviewer`.

A message that is no longer needed (the Reviewer has reviewed, the MR is gone) is skipped, also while it waits for your approval; `suica send` refuses it with `obsolete`. A Re-review Nudge is obsolete when the MR is gone, merged, closed or a draft, the Reviewer was removed, the Reviewer reviewed again since it was queued, or you re-requested them in GitLab. A reminder is due 24 hours after the nudge was actually delivered, never before.

Each flow has a send mode: `approval` (default; the message waits for you), `auto` (sent when due) or `dry-run` (rendered and recorded, never sent). Messages only go out in working hours (Mac local time) and wait in the queue otherwise.

When Re-review Nudges start waiting for you (in working hours, in `approval` mode), the agent shows one macOS notification per MR, in Indonesian: "Minta review ulang?", then "Kamu push ke <MR title> setelah <names> review. Kirim pesan Teams?". With `terminal-notifier`, clicking it opens Suica on **Messages → Your MRs** with that message selected (or the list, when several Reviewers of one MR are waiting). The click opens the link `suica://message/<id>` (or `suica://messages`), which the menu bar app registers: after updating, run `scripts/install-macos-app.sh` once so macOS knows the `suica://` scheme. Without `terminal-notifier` the notification is not clickable and the menu bar badge still shows the message. There is no notification in `auto` or `dry-run` mode, and a notification that fails to show is logged and not repeated; the message keeps waiting either way. The other held messages (nudges, reminders, notices) only change the badge.

```bash
suica pending [--all]   # list messages that need you (all statuses with --all)
suica send <id>         # send a pending message
suica skip <id>         # drop a message
suica retry <id>        # look the person up again after fixing teams.people
suica selftest          # send one test line to your own Teams notes chat
suica state             # the agent's state as one JSON document (used by the menu bar app)
```

Statuses in `suica pending`: `pending` waits for you; `unresolved` needs a `teams.people` line (then `suica retry`), or Teams returned an error for that person's lookup; `failed` is final; `sending` may have been delivered, so check Teams before deciding.

Templates are files in the templates folder: `nudge.txt`, `reminder.txt`, `notice.approved.txt`, `notice.changes.txt`, `notice.comments.txt`, `notice.findings.txt`, `notice.refindings.txt`, `notice.reapproved.txt`, `rereview.txt`. Edit them in the app under **Configuration → Message templates** (design: [message studio spec](docs/superpowers/specs/2026-10-20-message-studio-design.md)). Pick one under **Teams messages** and edit it as it will look: **B**, *I*, ~~S~~ (⌘B, ⌘I, ⇧⌘X) and **Link…** (⌘K) format the selection; **Insert placeholder** puts a placeholder at the cursor as a chip that moves and deletes as one piece; **Emoji** offers quick picks and the system Emoji & Symbols palette, and typing a shortcode such as `:tada:` turns into 🎉; **GIF…** takes an https link to a GIF (right-click a GIF on GIPHY, Tenor or anywhere → Copy Image Address), plays it, asks for a short description and remembers the last eight. **Markdown** shows the source; a template that uses Markdown the visual editor cannot show without changing it (`__bold__`, headings, lists, code) opens there with a note. **Variants**: **+** adds another version of the template and **−** removes the one shown; in the file they are separated by a line that is exactly `--- or ---`, and each message uses one, picked from its id, so a retry or an approval later writes the same text while different messages vary. The preview shows the message as Teams will, GIFs animated (loaded over https only, 10 s timeout, at most 5 MB). **Save** writes the file, **Use built-in** removes it and **Revert** drops your unsaved edit. A template with an unknown placeholder, an empty variant or an image that is not an `https://` link cannot be saved, and stops startup when written by hand. The agent reads templates when it starts, so **Restart agent** (offered after saving) applies them; messages already waiting keep their text. `suica templates show --json` and `suica templates set --json` (`{"name": …, "text": … or null}` on stdin) are what the app runs. Placeholders: `{{mr.link}}` (the MR title as a link to the MR, which the built-in templates use), `{{mr.title}}`, `{{mr.url}}`, `{{mr.iid}}`, `{{mr.project}}`, `{{person.name}}`, `{{person.firstName}}` (the first word of the name), `{{owner.name}}`, `{{agent.name}}` (`teams.agentName`), `{{time.greeting}}` ("pagi" from 04:00, "siang" from 11:00, "sore" from 15:00, "malam" from 18:00, local time when the message is written), `{{review.findings}}` (what the Agent Review found, such as "ada 8 findings (7 Minor, 1 Nit)"; empty in every template but `notice.findings`, `notice.refindings` and `notice.reapproved`; an Agent Re-review reports "ada 2 findings baru (1 Major, 1 Minor)"). Shortcodes (`:wave:`, `:pray:`, `:rocket:`, … the list is `emoji` in `suica templates show --json`) are replaced in the template only, never in a name or title filled into it; an unknown one stays as written. Messages are sent to Teams as Markdown, so `**bold**`, `_italic_`, `~~strikethrough~~`, `[text](url)` and `![description](https://….gif)` work, a line break is kept, and a bare URL is clickable too; names and titles filled into a template are escaped, so a title with `*`, `_` or brackets reads as written. The Teams MCP turns an image into an HTML `<img>`; whether Teams shows an image from another site inline was not verified, so check the first one in `approval` mode. The app shows a message waiting for approval the same way.

**Your notifications.** The macOS notifications the agent shows you have templates too, in the same folder and page: `alert.review-requested`, `alert.activity`, `alert.summary`, `alert.baseline`, `alert.rereview`, `alert.review-ready`, `alert.review-posted`, `alert.review-approved`, `alert.review-post-failed`, `alert.review-failed` and `alert.review-skipped` (`.txt`). The first line is the title and the rest the body; both are needed. They are plain text: shortcodes work, Markdown does not, and each part is cut to one line. Each has its own placeholders, which the page lists: `{{mr.title}}`, `{{mr.iid}}`, `{{mr.project}}`, `{{mr.url}}` and `{{author.name}}` for a review request; `{{activity.summary}}` ("Budi menyetujui; 2 komentar baru dari Rina") for activity; `{{alert.count}}` and `{{alert.titles}}` for the summary; `{{alert.count}}` when the agent starts; `{{reviewers.names}}` for a Re-review Nudge waiting; `{{review.reason}}` for a failed or skipped Agent Review. The page previews each as a macOS banner with sample values. The built-in texts are the ones described in this README. They load whether Teams is on or not, and a bad one stops startup like a bad Teams template. The failure notifications (GitLab login, Teams unreachable, state storage) keep their fixed text.

People are found through `teams.people`, then a cache, then a Teams search on the GitLab name: a Teams user with the same display name wins, and otherwise one whose display name is the GitLab name followed by more words (GitLab "Mufid Hadi", Teams "Mufid Hadi Abdulhakim"). When that leaves two or more people, the message is `unresolved` (`ambiguous`) and left for you.

## Moving from MR Review Assistant

Suica used to be called MR Review Assistant. If you ran it under the old name, run these three commands from the checkout, in this order:

```bash
scripts/migrate-to-suica.sh
scripts/install-cli.sh
suica agent install
scripts/install-macos-app.sh
```

`scripts/migrate-to-suica.sh` is a one-time move and is safe to run twice (a second run prints `already migrated` and changes nothing). It:

- stops the old LaunchAgent (`com.madhani.mr-review-assistant`) and quits the old menu bar app;
- refuses, before moving anything, if an old agent or app process is still running, if the old LaunchAgent is still loaded, or if any process (for example an agent started by hand with `npm start`) holds the old state database open;
- refuses, naming both paths, if an old folder and its new counterpart both exist (merge them by hand);
- moves `~/.config/mr-review-assistant` to `~/.config/suica`, `~/Library/Application Support/mr-review-assistant` to `~/Library/Application Support/suica`, and `~/Library/Logs/mr-review-assistant` to `~/Library/Logs/suica`, so the state database moves as it is;
- removes the old LaunchAgent plist and `~/Applications/MR Review Assistant.app`, so two menu bar icons never run against different paths;
- warns, without editing the file, for every line of the moved config that still names `mr-review-assistant` (for example an explicit `statePath` or `teams.templatesPath`; change those by hand);
- when it warns about such a line, ends by telling you to fix those keys first and only then run the install steps (an explicit old `statePath` would make the new agent recreate the old folder with a fresh database);
- warns if `MRA_CONFIG` is set. The agent and CLI no longer read it and refuse to start while it is set without `SUICA_CONFIG`: rename it to `SUICA_CONFIG` in your shell profile.

The migration deletes the old app bundle, so replace **MR Review Assistant** with **Suica** under System Settings → General → Login Items; an old Login Item would point at nothing.

If the script says an old process is still running: its process check also matches any process whose command line contains `mr-review-assistant` or `MRAMenuBar` (for example an editor or `tail` on the old log files, or a checkout folder still named `mr-review-assistant`). Close it or run the script from a renamed folder, then run the script again.

## Run in the background

```bash
suica agent install      # writes the LaunchAgent (com.madhani.suica.agent) for this installation and starts it
suica agent uninstall    # stops it and removes the plist
```

`suica agent install` refuses to run without a config file, writes `~/Library/LaunchAgents/com.madhani.suica.agent.plist` pointing at the installed `main.ts` and the `node` that runs the CLI, and reloads and starts the agent. Run it again after reinstalling the CLI elsewhere; `scripts/install-cli.sh` does that for you when the agent is already installed.

Logs are JSON lines captured by launchd in `~/Library/Logs/suica/` (`stdout.log`, `stderr.log`). The agent does no rotation. At the default log level it writes a line on start (with its main settings) and stop, the first poll's baseline, each Review Request, Reviewer state change and comment it detects, delivered notifications, pause and resume, each Agent Review queued, started, ready, posted, skipped or failed (with the reason), and each Teams message sent, held, skipped or failed. It logs errors once per failure streak and the recovery once the streak ends. Lines name MRs by key and messages and reviews by id, never a person. Actions run through the CLI (sending a held message, posting a review, approving) are not in these logs. Set `SUICA_LOG_LEVEL=debug` to see every poll. launchd restarts the agent only when it exits with an error, at most once a minute, and the installer refuses to run without a config file. The plist bakes in the absolute path of the `node` found when you ran the installer: re-run it after switching Node versions or moving the repository.

## Known limits

- Polling stops while the Mac is fully asleep; the next poll after wake (within about 15 seconds) catches up from stored state and collapses a burst into one summary.
- Do not run `suica once` while the background agent is running: the two processes are not coordinated and can alert on the same event twice.
- If a notification fails halfway, the ones already shown are not repeated and the rest are dropped (an error is logged and reported once).
- If the state database cannot be written, alerts can repeat until it recovers; you are told once.
- "GitLab unreachable" is only reported after two failed polls in a row, because the network is often not up yet right after a wake.
- When an MR is merged or closed there is no final alert (only open MRs are watched).
- A comment that arrives in the same poll in which an MR is first tracked, or in which a draft becomes ready, is recorded silently.
- More than 100 open MRs on either list fails the poll with a notification (pagination is not implemented).
- `osascript` notifications cannot be clicked; install `terminal-notifier` for click-to-open.
- A Teams message is sent at most once: a failed or interrupted send is never repeated automatically.
- An MR is announced to its Author only once per round of your review.
- A Re-review Nudge is judged from the MR's head commit, so a rebase or a merge of the target branch counts as a push. A review and a push that both happen between two polls look like one change and make no nudge, and only the last 50 notes of an MR are read, so on a very busy MR a Reviewer's new comment can be missed. A missed nudge is accepted; a duplicate is not.
- Teams planning starts from the moment Teams is enabled, and again after every period in which it was switched off; older history is never announced.
- An Agent Review reviews code by reading only (no tests, no build), and reviews the branch tip at clone time; if the author pushes between the diff and the clone, the diff and the checkout can differ by that push.
- Agent Review runs with Claude Code or Codex only. Codex gets the review skill's text but not the other skills it refers to. Gemini CLI is detected but not used for reviews.
- Automatic reviews spend your model quota on every MR waiting for you that the agent has not reviewed (capped by `review.maxPerDay`); set `review.auto: false` to start reviews only by hand.
- Which further skills the model reads while following the review skill can differ between runs and models.
- A model CLI installed outside the folders listed under Overview is not found; there is no setting for its path.
- The menu bar app shows what the agent last recorded and refreshes every 30 seconds; the background agent (or `suica once`) has to have polled for its list to be current.
- Statistics start once the background agent was restarted on this version: there is no history before that, and it is kept for 90 days. The turnaround times stay empty until a request and its review are both recorded. **People you review** and **Slowest approvals** count only from the version that added them: older reviews did not record the MR's author, and approvals of MRs before then were not timed.
- The window refreshes every 30 seconds while it is open; the Configuration form is loaded when you open that section or press Reload.
- Saving the config rewrites the whole file: comments and values are kept, but indentation is normalised and flow lists such as `[a,b]` are respaced. Inside a list (`ignoreAuthors`, the working days) and the `people` map, the comments of the entries that stay are kept, and so is the comment after the list; a removed entry takes its comment with it, and a list item you change becomes a new item without one.
- **Restart agent** runs `launchctl kickstart -k`, which stops the running agent. A poll in progress is not waited for, so a Teams message being sent at that moment can be cut off; it stays `sending` and may have been delivered, so check Teams before deciding.
- The CLI's wrapper and the LaunchAgent hold the absolute `node` path, and the app holds the absolute path of the `suica` command: after switching Node versions run `scripts/install-cli.sh` again, and after installing the CLI somewhere else also run `scripts/install-macos-app.sh` again. Moving or deleting the checkout no longer matters once both are installed.
- An install path (`SUICA_PREFIX` or the node path) containing `"`, `$` or a backtick breaks the wrapper that `scripts/install-cli.sh` writes; install under a plain path.
- The app and the CLI speak a versioned JSON format (`contracts/agent-state.v1.json`, `contracts/status.v1.json`, `contracts/stats.v1.json`, `contracts/usage.v1.json`, `contracts/config.v1.json`, `contracts/reviews.v1.json`, `contracts/mr-detail.v1.json`); an app built for a different version shows "The agent speaks a newer protocol. Rebuild the app."
- The menu bar app gives a Send 300 seconds to finish (the CLI's own worst case with the default Teams timeouts is 210 s). If you raise `teams.callTimeoutSeconds`, raise `sendTimeout` in `macos/Suica/Sources/SuicaCore/AgentClient.swift` and run the install script again.
